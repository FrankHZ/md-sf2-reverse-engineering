## 合同边界

本合同拥有从已提交战斗动作加目标输入到有序战斗演出命令流与瞬态奖励/动作状态的变换。它定义：

1. 累加器初始化与动作族路由；
2. 目标排序与逐目标处理顺序；
3. 物理路线的分支时间线；
4. 物品到法术委托与使用后损坏/消耗门；
5. Taros 与 Burst Rock 特殊构建边界；
6. 战斗演出消息命令的物理形状与静态源码语料。

它不拥有玩家或 AI 如何选择动作、合法目标如何形成、详细伤害/法术/奖励公式、持久演出回放、渲染呈现或战斗结果。那些仍属于[战场导航合同](../../contracts/battlefield-navigation.md)、[交战解决合同](../../contracts/combat-resolution.md)、[法术解决合同](../../contracts/spell-resolution.md)与[战斗控制生命周期合同](../../contracts/battle-control-lifecycle.md)。

可执行所有者是 `sf2-battle-actions-static-v1`，位于 `tests/fixtures/h2/battle-actions-static-v1.json`。研究所有者是[battle action script construction](../../../research/battle-actions.md)。这是静态 source/ROM 合同。既有 H3 测试夹具只在其自身接缝闭合下游公式与回放；本文档不把它们聚合成新的运行时黄金值。

## 规范构建状态

实现必须区分以下状态域：

| 状态域 | 合同角色 |
| --- | --- |
| 已提交动作 | 从玩家/AI 控制接收的行动者、动作族、物品/法术选择器与所选目标输入 |
| 目标列表 | 有序战斗员字节与动作族特定的临时排序元数据 |
| 瞬态累加器 | 构建演出时清除或更新的 EXP、金币、攻击类型与动作标志 |
| 演出命令缓冲 | 由独立 battle-scene 解释器消费的有序字命令与参数 |
| 持久战斗员状态 | 由下游回放所有者应用的 HP、MP、状态、物品、EXP 与金币结果 |

构建器不是渲染器，其临时计算不自动持久。重制若在选择动作时直接变更最终战斗员状态，就无法在无重构同一有序边界的适配器的情况下证明本合同。

## 顶层动作管线

**已确认静态顺序：** `WriteBattlesceneScript` 首先清除 EXP、金币、攻击类型与瞬态动作标志。然后按六个源码拥有的动作族之一构建目标：

- 物理攻击；
- 施放法术；
- 使用物品；
- Burst Rock；
- 混乱动作；
- 棱镜激光。

目标构建后，引擎总是对目标列表排序。随后按此顺序处理每个目标：

1. 切换当前目标状态；
2. 应用动作效果；
3. 处理敌人物品掉落接缝。

所有目标之后，引擎执行：

1. 行动者空闲；
2. 已用物品损坏/消耗处理；
3. 二连击验证；
4. 反击验证；
5. 可选 Burst Rock 爆炸重入；
6. 脚本终止。

Burst Rock 爆炸在最终结束前重入目标与动作配置。该有序列表是构建合同，不是对帧时序、动画时长、目标选择意图或哪些自然调用方到达每个族的声称。

## 物理路线时间线

**已确认静态：** 物理动作路线按顺序尝试以下阶段：

1. 闪避；
2. 基础伤害；
3. 会心一击判定；
4. 伤害应用；
5. 异常处理；
6. 诅咒伤害；
7. double/counter 判定。

源码确认的提前退出同样重要：

- 闪避绕过基础伤害、会心一击、伤害应用、异常与诅咒处理；
- 直接致命命中在异常、诅咒伤害与后续构建之前退出；
- 致命诅咒伤害在 double/counter 构建之前退出。

详细算术、HP 夹断、闪避/会心含义、反应回放、奖励入账与后续验证仍归[交战解决](../../contracts/combat-resolution.md)所有。本合同保留这些所有者如何被排序；它不复制或加宽其运行时用例。

## 物品使用与损坏路由

**已确认静态：** 使用物品解包物品定义的法术索引与法术等级，然后委托给普通施法路线。使用后处理把装备与普通物品分开：

- 非装备在使用后被消耗；
- 装备只在可损坏且被己方角色使用时进入损坏路径；
- 已损坏装备被摧毁；
- 完好可损坏装备调用共享随机/调试生成器，只在其结果为零时损坏。

零结果门是保真事实。没有所属 RNG 输入/范围/调用方状态，它不建立玩家可见概率；也不建立动画、消息时序、经济价值或预期风险。物品所有权、物品栏容量、Deals 与服务行为仍属于其独立合同。

## Taros 与 Burst Rock 门

### Taros

**已确认静态：** 无效攻击门是战斗特定的。只有己方角色用 Achilles Sword 对 Taros 的物理攻击设置瞬态标志 112 并避免无效切换。该战斗中其他对 Taros 的攻击被标记为无效。瞬态标志在重新评估前清除。

这不建立正常剧情可达性、玩家知识、渲染反馈或通用“Boss 弱点”系统。重制必须保持该精确合取与通用抗性或伤害公式分离，除非记录刻意设计变更。

### 目标排序与 Burst Rock

**已确认静态：** 主目标排序把无符号战斗员字节升序排列。Burst Rock 接收一个临时排序位，使它们排在普通目标之后。第二遍把已标记 Burst Rock 按 HP 高到低排序，把最弱的留到后面，然后在返回前清除每个条目的临时排序位。

排序控制构建顺序。它本身不定义目标选择意图、同时效果语义、可见动画顺序，或下游回放合同之外的持久变更顺序。

## 战斗演出消息命令形状

源码宏 `displayMessage` 与 `displayMessageWithNoWait` 发出命令字 `0x10` 与 `0x11`。独立解析的 battle-scene 分发器把它们映射到 `bsc10_displayMessage` 与 `bsc11_displayMessageWithNoWait`。

两个宏都按此顺序发出六个运行时字（12 字节）：

| 字 | 运行时槽 |
| ---: | --- |
| 0 | 命令 |
| 1 | 消息 ID |
| 2 | 战斗员 |
| 3 | 物品或法术 |
| 4 | 保留零 |
| 5 | 数值 |

`writeBscParam` 贡献一个运行时字。其地址寄存器源形式发出两次字节写入；普通源形式发出一次字写入。这些汇编后的 68000 指令形式必须与 12 字节运行时命令缓冲记录保持可区分。

命令 `0x10` 对 `0x11` 是静态分发器区分。宏名不证明观察到的等待、输入、服务完成或呈现行为；那些在排队的成组运行时观察存在之前保持 **未知**。

## 完整消息站点语料

**已确认静态语料：** 跨全部 29 个 battle-action 文件，有 54 处直接消息宏使用，分布于 11 个正面与 18 个零使用文件：

- 49 个 `displayMessage` 站点；
- 5 个 `displayMessageWithNoWait` 站点。

全部 54 个源码形式绑定到固定的 H1 列表。四十三个操作数是针对连续 4,267 行 ID 域解析的立即数 `#MESSAGE_*` 符号。其余十一个动态操作数有有限、源码派生的候选域：

- 四个动作消息站点覆盖攻击类型、法术选择器、混乱受限偏移与棱镜激光选择器；
- 伤害、死亡与法术路线保留其源码派生的赋值集；
- 两个物品损坏调用方把损坏（`d0=0`）或摧毁（`d0=1`）传入 25 行 `itemBreakMessage` 表。

物品损坏表加其 `0xFFFF` 哨兵占用已验证的 H1 范围，并在两个调用方各给出十个消息候选。跨动态站点，测试夹具记录 56 次候选出现与 56 个域内不同行 ID。受追踪合同只保留符号与数字 ID；它不解码或复现受版权保护的对话文本。

这些候选域是静态可能性边界。它们不证明正常调用方可达性、频率、特定通关中的所选文本、立绘/布局行为或渲染时序。

## 法术选择器源码顺序

消息选择器首先把 battle-scene 法术索引与 Spoit 到 Atlas 比较，然后在默认赋值之前为 Aqua 与 Aqua 2 级专门重新加载 `BATTLEACTION_OFFSET_ITEM_OR_SPELL(a3)`。暴露源码兼容消息选择的适配器必须在 fixture 接缝保留该选择器/默认/覆盖顺序。

这不是每个选择器自然可达或消息名描述完整法术效果的证据。法术解决仍由专用合同拥有。

## 未使用与呈现辅助

`nullsub_BBE4` 加源码拥有的 sleep/NOP 辅助文件被清单化但不声称可达。动作/死亡消息、法术/物理动画、诅咒伤害与异常辅助条目有 H1 绑定立足点；其更深的呈现与未建模子路线不由本合同提升。

实现不得仅因未使用辅助有源码标签或地址就创建必需游戏行为。反过来，省略可达呈现效果也不能仅由静态清单证明；该问题保持 **未知**。

## 保真与现代化边界

原版保真动作构建器必须保留：

- 不同的已提交动作、目标列表、累加器、命令缓冲与持久状态接缝；
- 累加器重置、动作族路由、目标排序、逐目标与目标后顺序；
- 物理路线提前退出；
- 物品到法术委托与精确装备损坏/消耗门；
- Taros 合取/标志行为与 Burst Rock 临时排序；
- 消息命令字、六字布局、参数发射单位与源码派生候选域。

未来重制可以使用类型化命令、数据驱动动作图、不同内部集合、并行视觉效果、更快/可跳过呈现、更丰富日志或重新设计的特殊门。那些是产品决定，不是原版事实。fixture 可见偏差需要显式决定与 H4 expected-deviation 覆盖。

## H4 验收面

未来 H4 适配器应消费 `sf2-battle-actions-static-v1` 并比较：

1. 每个受支持动作族的初始累加器状态；
2. 排序后的目标字节与已清除的 Burst Rock 排序元数据；
3. 有序逐目标与目标后事件轨迹；
4. 不在此适配器中重新实现下游算术的物理提前退出轨迹；
5. 源码形状输入的物品委托与损坏/消耗分支结果；
6. Taros 合取/标志结果；
7. 精确消息命令记录与静态候选域选择。

下游 HP/MP/状态/EXP/金币/物品持久性必须与拥有那些结果的战斗、法术与回放测试夹具比较。H4 不得用一个聚合战斗黄金值替代这些独立边界。
